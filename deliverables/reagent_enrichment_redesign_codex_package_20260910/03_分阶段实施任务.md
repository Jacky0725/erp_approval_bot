# 分阶段实施任务

## 阶段 0：基线、样本集和观测性

目标：在改变行为前建立可信基线。

任务：

- 从 `approval_suggestions_all.xlsx`、人工复核队列和试剂记忆生成去标识化 benchmark；按中文名、英文名、CAS、错误 CAS、商品名、混合物、盐/水合物、高风险类别分层。
- 默认至少 200 个已人工确认样本；高风险类别样本不足时全部纳入。
- 增加单试剂 trace id、provider 请求数/耗时/状态、缓存命中、LLM 调用次数/耗时/token、字段覆盖率、人工复核原因码。
- 将临时故障、查无结果、身份冲突、字段不足拆成不同 reason code。
- 增加只读 benchmark 命令，输出 JSON 和 Markdown 汇总。

涉及文件：`src/stage_logger.py`、`src/chemical_searcher.py`、`src/llm_extractor.py`、新增 `src/enrichment_metrics.py`、新增 benchmark 脚本和测试。

完成条件：能在不访问 ERP、不写生产文件的情况下重复运行基线；相同输入生成相同样本 ID；指标能回答每条记录花了多少网络请求和 LLM 调用。

## 阶段 1：确定性名称清洗与身份契约

目标：让名称清洗完全本地化，身份状态明确。

任务：

- 将 `NameNormalizer.normalize()` 中的 LLM 调用移出默认路径；保留兼容开关，但新链路禁用。
- 清洗时保留 `base_name/concentration/grade/package/salt_or_hydrate/mixture_markers`，避免直接丢弃信息。
- 实现 CAS 校验位和非法 CAS 状态；CAS 与名称冲突时保留两个候选，不静默覆盖。
- 新增 `IdentityRecord` 和序列化校验。
- 建立审核别名索引，按 CAS、规范化别名和英文名做 O(1) 查询。
- 保持旧 API 适配层，避免一次改完所有调用方。

涉及文件：`src/name_normalizer.py`、新增 `src/reagent_identity.py`、`src/reagent_memory.py`、测试。

完成条件：名称清洗零网络、零 LLM；旧测试通过；benchmark 中的已知 CAS 身份准确率不下降；所有冲突都显式进入人工复核。

## 阶段 2：结构化 provider 适配器与双阶段批量查询

目标：消除逐条查询长尾和配置假象。

任务：

- 定义 `ChemicalSourceAdapter`：`resolve_many()`、`fetch_evidence_many()`、能力声明、错误分类。
- 将 PubChem 代码迁入适配器，身份批量解析与 PUG REST 属性批量拉取分开。
- PUG View 采用受控并发，仅请求实际缺失的 heading/字段。
- 删除生产 provider 链中的硬编码，配置中只有已实现且通过健康检查的 provider 才能启用。
- CompTox 放在 feature flag 后；无 API key 时状态为 `disabled_missing_credentials`，不能假装查询失败。
- NIST 只声明其支持字段，不用它填充无法可靠提供的危害字段。
- 中文站点适配器保持 disabled/background_only；503 不阻塞当前批次。
- 实现跨线程 single-flight 和批次总 deadline。

涉及文件：新增 `src/chemical_sources/`，收敛 `src/chemical_searcher.py`，更新配置和测试。

完成条件：20 个去重后的可由 PubChem 解析的样本不会执行 20 套完整 provider 链；配置与真实适配器清单一致；503 注入测试能快速熔断且不污染负缓存。

## 阶段 3：字段级证据解析与 LLM 按需补缺

目标：将网页文本和模型输出从事实层解耦。

任务：

- 新增 `EvidenceItem`、`ResolvedProperties`、单位标准化和冲突策略。
- 为 PubChem JSON、PUG View 和供应商 SDS 的关键字段实现确定性解析器。
- 根据当前规则计算 `missing_decision_fields`，只请求会影响判定的字段。
- 合并名称候选生成、物性抽取和人工建议的重复 LLM 路径。新链路每个身份正常最多一次 LLM 调用。
- LLM 输入必须是可信文本和明确缺失字段；输出包含 evidence span，无法定位原文的值标记为 `predicted` 或丢弃。
- 将模型知识型建议单独存放，永不升级为外部证据。

涉及文件：新增 `src/evidence_resolver.py`、`src/evidence_parsers/`，收敛 `src/llm_extractor.py` 和 `src/approval_flow.py`，测试。

完成条件：有完整结构化证据时 LLM 调用为 0；无可信证据时不执行“模型知识 → 自动判定”；冲突字段不会被后到来源覆盖。

## 阶段 4：规则引擎输入收敛和 Excel 规则接入

目标：让判定完全可解释、可版本化。

任务：

- RuleEngine 新增 typed-input 入口，旧字典入口保留兼容。
- 每条判定记录 rule id、规则文件哈希、证据引用和 reason code。
- 把可配置阈值、名称名单和特殊条件逐步迁入结构化 Excel；程序只保留通用执行语义和安全保护。
- 对用户回传的规则 Excel 做 schema 校验、重复 rule id、未知类别、非法 condition、阈值单位、优先级冲突检查。
- 增加规则差异报告和 benchmark 回放，规则变化不得直接覆盖生产文件。

涉及文件：`src/rule_engine.py`、`src/rule_maintainer.py`、`config/rules_structured.xlsx` 导入流程、测试。

完成条件：每个自动建议都能从类别追溯到 rule id 和 EvidenceItem；规则文件不合法时拒绝加载并保留上一版本。

## 阶段 5：影子运行、灰度切换和 UI

目标：用真实工作负载验证后再切换。

任务：

- 新旧链路并行计算，但 shadow 结果不写 ERP。
- 管理 UI 展示性能、provider 健康、字段覆盖、差异原因和人工复核率。
- 先对普通类/低风险身份明确样本启用新链路，再扩大到高风险类别；高风险切换需要 benchmark 达标。
- 保留一键切回 legacy enrichment 的配置开关；缓存 schema 各自版本化。
- 连续运行至少 7 个工作日后再移除旧路径，且需单独评审。

涉及文件：`src/approval_flow.py`、`src/web_app.py`、`src/web_runner.py`、dashboard 模板/CSS/JS、配置和测试。

完成条件：满足 `04_验收与回滚方案.md`；回滚不需要数据库降级或修改 ERP 数据。
