# Codex 主执行提示词

你正在 `D:\codex\reagent-approval-bot` 中重构试剂信息处理链路。先完整阅读根目录 `AGENTS.md`，再依次阅读本执行包中的 README、客观分析、目标架构、分阶段实施任务、验收与回滚方案和配置草案。

目标是重构“名称清洗 → 身份查询 → 物化信息提取 → 规则判定”，提高速度、稳定性、可解释性和中文试剂名称的实际命中率，同时保持 ERP 写入安全边界。

执行要求：

1. 严格按阶段 0 到阶段 5 实施。每个阶段先检查相关代码、测试和未提交修改，避免覆盖用户工作。
2. 每个阶段开始前记录基线，完成后运行该阶段相关测试和 benchmark；未通过验收门槛时修复，不得跳到下一阶段。
3. 使用 feature flag 和 shadow mode。阶段 5 达标前，新链路不得改变 ERP 实际写入结果。
4. 保留 `src/browser_bot.py` 旧入口；新逻辑放在职责明确的模块中，并保持 `approval_flow.py` 只负责流程编排。
5. 名称清洗必须本地、确定性、零网络、零 LLM。LLM 只允许生成待验证身份候选，或从可信文本抽取明确缺失字段。
6. 先解析身份，再获取证据；优先结构化 API 和供应商 SDS。中文商业网站不得进入同步关键路径。
7. 实现字段级 provenance、单位标准化、三态值和冲突保留。LLM 模型知识不能成为自动审批证据。
8. RuleEngine 必须输出 rule id、规则文件版本、evidence refs 和 reason codes。用户回传的 Excel 规则通过校验和 benchmark 后再发布。
9. 网络调用必须有批次总 deadline、source 级限流、有限重试、熔断和正确的负缓存语义。503/超时不能写成长期“未找到”。
10. 先修根因；不要通过提高重试次数、扩大超时或增加无约束线程掩盖问题。
11. 不做与本链路无关的重构，不改真实凭据，不提交 `.env`，不自动审批高风险或身份不确定记录。
12. 每个阶段结束时汇报：改了什么、为什么、测试结果、benchmark 前后对比、已知限制和下一阶段进入条件。
