# 客观分析与推荐方案

## 结论

当前问题的主因不是“缺少一个更支持中文的网站”，而是身份解析、数据检索、文本抽取和判定之间缺少稳定契约，导致同一试剂被重复标准化、重复调用 LLM、逐个尝试查询，并把网站故障、查无结果和身份冲突混在同一结果与缓存中。

推荐采用“身份优先、结构化数据优先、字段级证据合并、LLM 按需补缺、规则纯确定性”的分层架构。PubChem 继续作为默认公开数据源；供应商 SDS 或人工上传 SDS 是混合物与商品试剂的优先证据；EPA CompTox 作为需要 API key 的可选增强；NIST 仅用于适合的实验物性字段。Chemsrc、ChemicalBook 等中文商业站点退出同步关键路径，只保留人工检索链接或后台低频补充。

## 已验证事实

### 1. 名称处理和 LLM 职责重复

- `NameNormalizer.normalize()` 在本地 CAS、别名、缩写未命中后调用 LLM 生成标准名。
- `ChemicalSearcher.search()` 又创建 `NameNormalizer`，有 CAS 时还会分别执行“带 CAS”和“不带 CAS”两次标准化。
- PubChem 批量预取阶段再次为每个项目创建并调用 `NameNormalizer`。
- 查询失败路径还能调用 LLM 生成搜索词、知识兜底或人工复核建议；之后正常流程还会调用 LLM 提取物化字段。

影响：一次 LLM 响应慢或失败，会同时拖慢身份、搜索和提取；结果也难以判断来自网页、模型知识还是规则推断。

### 2. 批量流程仍存在逐条串行段

`ChemicalSearcher.search_many()` 先预热 PubChem，但随后按试剂逐条执行 `search()`；混合物组分也在循环内逐条查询。当前配置的单项查询预算是 30 秒、批次预算 180 秒，名称最多尝试 4 个，网络请求最多重试 3 次。虽然 LLM 提取有 3 个线程，查询关键段仍可能形成长尾。

### 3. 配置与真实 provider 链不一致

`config/settings.yaml` 声明了 `pubchem/comptox/nist`，但生产路径 `_provider_chain()` 实际只返回 PubChem；另外两个 provider 没有真正进入运行链路。这会让运维人员误以为已有三源冗余。

### 4. 中文网站故障是放大器，不是根因

历史日志确实记录了大量 ChemicalBook 503 和 Chemsrc 超时；熔断器已经存在，但此前失败仍消耗了多个重试和查询词的时间。当前配置已关闭两站，这是正确的止损措施，但它没有解决中文名称到稳定身份标识的转换问题。

### 5. 缓存粒度和失败语义不够清晰

当前缓存用一个 payload 保存整次搜索结果，key 含整个搜索配置摘要。任一相关设置变化可能使大量有效缓存失效。`need_manual_review` 或任意 `failure_reason` 都按失败 TTL 处理，身份冲突、事实不足、404 未找到、503 临时故障之间没有独立缓存策略。

### 6. 决策层已具备安全意识，但输入仍是松散字典

现有规则引擎包含高风险优先级、浓度阈值、混合物最高风险、证据不足转人工等保护；但输入字段来自多个自由文本和布尔值，缺少统一单位、三态值、字段来源和冲突状态。LLM 抽取的 `true/false/null`、网页关键词和名称特判容易在同一层混合。

## 外部数据源的客观边界

- PubChem PUG REST 支持按名称、CID、InChIKey 等标识查询，也支持一次查询多个 CID 的属性；官方教程同时提醒，名称到结构本身可能不唯一，过大的请求可能在 30 秒后超时。因此应把名称搜索用于候选生成，用 CAS/CID/InChIKey 和交叉核验完成身份确认，并使用中等大小批次。[PubChem PUG REST](https://pubchem.ncbi.nlm.nih.gov/pug_rest/PUG_REST.html)；[PubChem 教程](https://pubchem.ncbi.nlm.nih.gov/docs/pug-rest-tutorial)
- PubChem PUG View 可按单个 CID 返回注释型数据，适合提取危害和实验物性，但不支持把多个 CID 放在同一个 PUG View 请求里。因此应在身份批量解析后，对仍需补充的 CID 做受控并发和字段缓存。[PubChem PUG View](https://pubchem.ncbi.nlm.nih.gov/docs/pug-view)
- EPA CompTox 提供化学身份、物性和毒性数据，并支持 POST 批量查询，但需要免费申请个人 API key。它适合作为可选增强，不应成为没有 key 时的硬依赖。[EPA CTX API](https://www.epa.gov/comptox-tools/computational-toxicology-and-exposure-apis-about)
- NIST Chemistry WebBook 可按 CAS、名称和公式查询实验数据，但覆盖字段和化合物范围不同。它适合补充沸点、热化学等实验数据，不适合作为统一危害分类源。[NIST Chemistry WebBook](https://webbook.nist.gov/chemistry/)
- CAS Common Chemistry 有 API，但当前需要申请访问，并存在单独许可条款。只有在组织确认授权和使用范围后，才应作为可选身份解析器接入。[CAS Common Chemistry API](https://www.cas.org/services/commonchemistry-api)

## 方案比较

| 方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| A. 继续增加中文网站并优化重试 | 改动小，中文名称可能更易命中 | 503、反爬、HTML 变动、许可和稳定性不可控；重试会继续放大长尾 | 不推荐作为主方案 |
| B. 只用 PubChem + 现有 LLM | 依赖少，改造较快 | 商品名、混合物和长尾中文名覆盖不足；LLM 仍承担过多身份责任 | 可作为过渡版本 |
| C. 分层证据架构（推荐） | 可追溯、可缓存、可批量、可降级；数据源可插拔 | 初期需要定义契约和迁移旧缓存/调用方 | 推荐 |
| D. 采购商业化化学数据库 | 身份和别名覆盖通常更强，SLA 更可控 | 成本、许可和采购周期未知 | 中长期可评估 |

## 推荐方案的关键决策

1. 名称清洗必须是本地、确定性、无网络的纯函数；保留原始名称和被删除片段。
2. CAS 先做格式与校验位验证，但 ERP CAS 只作为候选身份，不能因为格式正确就自动信任。
3. 将“身份解析”和“物性证据获取”分成两个批次，先得到稳定的 `identity_id`，再按缺失字段拉取详情。
4. 结构化 JSON/API 优先于网页正文；供应商 SDS 优先于聚合页面，尤其是混合物。
5. 每个字段单独保存来源、单位、原值、标准值、时间和置信等级；冲突不被覆盖，而是显式进入人工复核。
6. LLM 最多承担两类任务：无法确定身份时生成少量候选；非结构化证据无法用规则解析时抽取缺失字段。正常情况下每个试剂最多一次 LLM 调用。
7. LLM 只能抽取或提出候选，不能把模型知识伪装成外部证据，也不能直接触发自动审批。
8. RuleEngine 只消费已经标准化且带证据状态的字段，输出完整 decision trace。
9. 所有网络失败采用“快速失败 + stale-if-error”；503 不写入长期未找到缓存。
10. 使用 shadow mode 对旧链路和新链路并行比较，达到质量门槛后再逐步接管。
