# 客观分析与推荐方案

## 结论与证据边界

建议采用渐进式模块整理和操作台体验优化。现有架构已有清晰业务分层、模板拆分、设计变量、任务互斥与较丰富的测试，直接整体重写会丢失这些积累，并与当前未提交的 V2 补全改动冲突。

本轮进行了静态代码审查与 64 项针对性测试，没有启动管理服务或 ERP，没有查看真实运行数据、凭证或页面截图。以下视觉意见均为待验证的设计方向；不能视作已完成的 UX 审计或无障碍合规结论。行号仅对应本包创建时快照，执行前应重定位。

## 已验证事实

| 事实 | 证据 | 判断 |
| --- | --- | --- |
| UI 已拆分 | `src/templates/dashboard.html:1` 继承 layout，按 active_page 引入八个 partials；`src/templates/layout.html` 引入独立 JS | 不应按旧描述重新做一次模板拆分 |
| CSS 已有设计系统基础 | `src/static/dashboard.css:13` 起有颜色、间距、8px 圆角等变量，存在多组媒体查询和 focus-visible | 应整理现有规则，而非另建一套全局主题 |
| 核心文件规模偏大 | web_runner 2608 行，approval_flow 3831 行，approval_writer 2038 行，chemical_searcher 2817 行，dashboard.js 1866 行，CSS 4398 行 | 规模是检查职责的线索，不是缺陷或强制拆分指标 |
| 轮询缺少统一保护 | `dashboard.js:1709` 的 refreshStatus 直接 fetch/json，末尾 `:1864–1866` 直接调用并 setInterval 2500ms；该函数没有全局 in-flight、超时或 catch | 慢请求可能重叠，失败可能保留旧状态并产生未处理拒绝；实际频率和影响需故障注入验证 |
| 启动 UI 有后台副作用 | `web_app.py:72–80` lifespan 调用 scheduler.start 和 dingtalk_stream_bot.start | 不能直接拿真实配置启动第二个服务做页面检查；是否实际触发任务依赖配置，本轮未判断 |
| 已有进程内任务互斥 | `web_runner.py:262` 的 start 在 RLock 内检查 running | 不应笼统报告“没有防重复执行”；跨进程、多入口及崩溃恢复仍需验证 |
| 下载路径已有约束 | `web_app.py:667` resolve 后检查 relative_to(log_dir) | 不应报告未经验证的路径穿越漏洞；重构时保留此行为并补边界测试 |
| 结果兼容逻辑有语义歧义 | `approval_batch_state.py:20` 使用 `raw_result.get('handled') or 全部建议键`；现有测试明确接受 legacy None -> all handled | 显式空集合与缺省值被合并；handled 可能是终态而非保存成功，不能直接改成“失败” |
| Excel 辅助器直接写目标文件 | `excel_exports.py:17–24` 直接 to_excel，锁定时按秒生成备用文件名 | 原子替换、并发唯一性值得评估；不能据此声称已发生数据丢失 |
| UI 文本已经部分转义 | `dashboard.js:650` 定义 escapeHtml，多处渲染使用 | 不应仅因 innerHTML 存在就断言 XSS；应逐个核验动态文本和 URL 协议 |
| 新补全链路已在建 | 现有 `reagent_enrichment_redesign_codex_package_20260910/05_实施状态_20260910.md`、enrichment_v2、identity、evidence、sources 及测试 | 状态文档是历史记录，不能替代当前验收；禁止另建竞争实现 |

## 优先级

1. **P0：隔离与基线。** 当前未提交变更多，先记录文件哈希、既有接口、模板字段、测试结果；将 UI 预览隔离于调度、钉钉、同步、更新和 ERP 写入。
2. **高优先级验证：写入结果与恢复。** 跟踪 legacy None、显式空 handled、部分成功、超时、重读和重试耗尽。验证完成前保留行为，不把推断变成修复。
3. **高优先级修复候选：前端请求可靠性。** 注入网络失败与乱序响应后，统一错误、超时、防重入和编辑保护。
4. **中优先级：职责与持久化。** 整理 web_runner、approval_flow 中经证据确认的重复和耦合；检查 Excel/队列/记忆库跨存储的部分提交。无数据迁移默认采用兼容封装。
5. **中优先级：操作台体验。** 聚焦运行、复核、建议证据、异常定位；用当前截图验证信息密度与窄屏表现。

## 方案比较

| 路线 | 收益 | 成本与局限 | 推荐 |
| --- | --- | --- | --- |
| 仅调整 CSS | 变更小，外观一致性改善快 | 不能解决轮询可靠性、状态语义和跨层耦合 | 只作为一个阶段 |
| 保留技术栈，模块与交互渐进优化 | 兼容安装包、现有接口和规则，容易逐批回归 | 仍需治理 JS/CSS 边界 | **主方案** |
| React/Vue + API 全面迁移 | 有利于复杂前端团队独立开发 | 新构建链、打包兼容、接口迁移和大量回归；当前缺少需求证据 | 暂缓，有明确需求再立项 |
| Figma 先行再落地 | 有利于多人视觉评审和组件规范 | 多一个同步环节；设计文件不证明业务正确 | 可选，不阻塞主方案 |

## 不做的推断

没有基准数据时不承诺性能提升比例；不以历史测试数量宣称当前全量通过；不以截图替代交互验证；不把正式安装包无头模式与源码开发 headed 模式混为一谈；不假设所有下载、同步和更新动作都是只读。
