# 钉钉机器人优化评估

以下建议基于当前仓库检查与公开项目文档，是工程判断，不代表已全部实现。
不建议直接迁移到大型机器人框架：当前只有一个平台和有限业务动作，迁移成本大于收益。

## 优先级一：可靠性和安全边界

- 已实现任务级通知目标：启动前持久化任务 ID 与目标群快照；消息查询不改通知目标，
  新任务或其他群消息不改变旧任务的结束通知目标。
- 已实现 SQLite 持久化去重：同一钉钉消息 ID 在进程重启后不再次触发审批。
  执行前先记账，结果不明不自动重放；仍不宣称消息层提供跨系统“恰好一次”。
- 已实现业务回执校验、临时回复地址有效期检查和同群备用发送，明确限流最多3次尝试；
  结果不明的发送不重放，ERP 审批不跟随通知重试。
- 已区分线程存活和实际连接，显示最近连接、接收与重连次数；模型配置完整不等于服务已验证可用。
- 保持并固定已安装的 SDK 0.24.3，增加受控连接层，不直接安装尚未验证的主分支代码；
  SDK 负责协议解析和 ACK，连接层负责超时协商、关闭、心跳、退避和清理旧回调。
- 已去掉备用发送中的伪 `@all` 字样；普通主动群消息接口的已核验请求模型没有提醒参数，
  备用通道发送摘要时记录提醒降级，实际 @所有人 仍待群内验收。

参考：[钉钉官方 Python SDK](https://github.com/open-dingtalk/dingtalk-stream-sdk-python)。
官方 SDK 展示异步处理、去重及停止重连等机制；本项目借鉴模式，不盲目替换运行依赖。
接口字段参考：[官方生成的机器人 OpenAPI SDK](https://github.com/alibabacloud-go/dingtalk/blob/master/robot_1_0/client.go)。

## 优先级二：提升日常操作体验

- 按任务 ID 查询最近结果，显示已处理/待处理/失败/需人工条数、当前阶段和耗时。
  任务进度应使用结构化事件，而不是长期依赖日志正则解析。
- 先提供“停止后续批次”的优雅停止，明确当前 ERP 提交可能已经完成。
  不应把“取消对话”和“中断审批进程”合并；强制停止需额外权限和确认。
- 使用交互卡片提供确认、取消、查看状态，减少确认码输入，但卡片回调也必须校验发起人、期限及一次性消费。
- 通知采用失败即时、成功汇总和分阶段节流，保留现有 @所有人 规则，任何改动需用户确认。

参考：[NoneBot 会话控制](https://nonebot.dev/docs/appendices/session-control)、
[钉钉官方卡片实现](https://github.com/open-dingtalk/dingtalk-stream-sdk-python/blob/main/dingtalk_stream/card_replier.py)。
NoneBot 的参数收集和会话状态适合借鉴；当前不需要为了这几个命令引入整个框架。

## 优先级三：按实际需求扩展

- 保留当前“群成员都能运行审批”，未来若新增改规则、重试异常批次、改配置或强制停止，
  这些动作应单独设管理员权限，而不是继承当前运行审批权限。
- 可增加规则版本、运行记录等只读问答；引用真实记录并标注时间，不能让模型编造原因。
- 暂不建议开放任意 Shell、任意 MCP 工具、聊天直接改规则，或直接由大模型批准试剂。
- 暂不优先做语音、图片识别、跨平台适配和复杂长期记忆；它们会增加权限、维护与数据泄露面。

参考：[Errbot](https://github.com/errbotio/errbot) 的命令级 ACL 和会话流程。
借鉴权限分层，不照搬其从聊天安装插件等管理能力。

## 当前版本已做

精确指令直达、自然语言执行二次确认、发送人和会话绑定、确认配置复核、
对话上下文隔离、限流、输入输出限长、敏感信息拦截、模型错误降级、异步模型调用、
持久化消息去重、任务级通知目标快照，以及不记录消息原文的动作审计。

未做真实群联调前，不应把上述测试结果等同于生产可用性或钉钉平台权限已验证。
