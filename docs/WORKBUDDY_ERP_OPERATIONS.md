# WorkBuddy 的 ERP 匹配和试剂库处理

Web UI 使用现有的 WorkBuddy 批次循环入口，ERP 写入后端选择已验证的接口写入。

- 正式运行准备新批前，先执行整张清单的一键匹配，回读后只将类别仍为空的记录发送给 WorkBuddy。测试模式只读。
- 写入模式“仅保存”保持只填写、保存类别；“保存并生成试剂库”在类别保存并回读成功后，再调用 ERP 的明细生成试剂库接口。
- 新建须回读确认新记录和类别。ERP 明确返回“已存在、没有修改项”或要求确认修改已有库记录时，保留原记录，不覆盖，继续后续批次；请求失败或无法确认写入结果时仍停止核对。
- 类别保存与入库结果分别记录在批次 state.json，并写入审计日志。入库未完成时保留 result.xlsx、停止循环，避免类别保存被误报为失败后重复保存。
- 接口结果不明或报错时不自动重复入库。先核对 ERP 及批次状态；不能通过删除检查点或重新建批代替核对。
- 这两项操作不点击审批清单的“通过”。

## 候选优化与发布条件

- `workbuddy.compact_rules` 为 `false` 时沿用 XLSX 读取。开启后，已审阅规则的发布同时生成带源 SHA-256 的紧凑缓存。正式 XLSX 仍是规则源。每段 UTF-8 文本最多 12,000 字节。批次复制并校验分段，发送前缺失或损坏时回退本批 XLSX。发送后发现文件被修改时暂停导入。
- `workbuddy.reuse_chat` 为 `false` 时逐批新开任务。开启后，已完成批次的规则版本、读取格式及原对话均可确认时，允许继续第二、三批，第四批新开任务。发送结果不明时核对原批次，保留既有恢复记录。
- `workbuddy.freeze_web_todo_scope` 为 `false` 时 Web UI 全量任务每轮查询 ERP。开启后首次查询固定范围。钉钉全量任务已有此行为，指定清单按原选择运行。
- 开关均默认关闭。只在隔离桌面通过同模型对照、三批续聊和第四批切换后并入。隔离项目和后续正式验证使用 `WORKBUDDY_PROJECT_INSTRUCTIONS.txt` 中更新的项目指令。同一会话连续三批和第四批切换使用隔离 Web UI、真实 WorkBuddy 与模拟 ERP 验收。正式待办量自然达到相应批次时，再核对线上表现。

需要在当前审阅规则上预先生成缓存时，在对应运行根目录空闲期间执行以下命令。它只生成对应版本的派生缓存。

## 单条待复核与继续处理

- WorkBuddy 明确输出「需人工复核」且同批其他记录已完成时，保留原结果及记录 ID，循环继续处理其他空项。待复核明细保持排除，即使规则版本更新。清单仍有空白的待复核行时，跳过该清单的整表一键匹配。
- 完全无关的批次不影响本次清单。存在部分重合的未完成批次时，按日志选择原批次全部清单。人工停止和 ERP 写入、入库待核对仍走原恢复流程。
- WorkBuddy 全量循环从 ERP 读取并固定最新待办。选择「全清单分页保存」或「保存并生成试剂库」、且 AUTO_PASS 关闭时，可隔离明确已投递但尚未导入或写入的暂停批次。不导入迟到结果、不重发，所在清单跳过整单一键匹配，其余空白明细照常处理。钉钉「执行审批」沿用本机默认写入模式；无法核实的暂停任务仍然拦截。
- 复核后先由操作员在 ERP 保存确认的类别。在运行目录的 `data/workbuddy_review_confirmations/<批次ID>.json` 写入记录 ID 与已保存的 ERP 类别，例如 `{"<记录ID>":"普通类"}`。随后在 Web UI 指定原批次全部清单并点击「导入 WorkBuddy 结果」。程序回读核对 ERP 身份和类别，再按原批次的写入模式收尾。原 WorkBuddy 判定和已经完成的入库记录保留。

## 升批验收

保持每批 20 条为基线。使用同一组输入、同一规则版本和固定模型，对比现行同会话续聊与拟提高的批量。至少跑两轮并交换顺序，记录从组批到结果校验通过的总耗时。

每轮两种跑法都必须包含未提供浓度的「高氯酸滴定液,乙酸基质」。类别应为「易爆类」，判断依据须按 `SPECIAL-EXP-004` 说明输入未提供浓度。对隔离对照产出的 `benchmark.json` 运行 `python scripts/check_workbuddy_batch_size_acceptance.py <benchmark.json>`。此项通过后仍需核对其他关键规则、分类一致性和耗时，才能安排正式 ERP 单批试跑。

## 固定结果写表与恢复

- `workbuddy.fixed_result_writer` 默认关闭。开启后，新批次带有固定脚本。WorkBuddy 填写 UTF-8 `judgments.json` 并运行 `python write_result.py`。导入时独立核对五列 Excel 与原始判定，成功收尾后清理这两份交付文件。
- 结果尚未导入且依据残缺时，先确认原批次、规则版本和 ERP 写入状态。保留坏文件的副本，用原批次的完整判定生成新结果。已有固定脚本的批次使用其原脚本，旧批次使用当前发布版附带的同一脚本。再从现有 Web UI 导入或批次循环入口继续。
- 已记录结果摘要时，按原摘要检查并从已有进度恢复。类别或入库状态存在不确定性时先回读 ERP，再处理原批次。

## 自动接续与 Web UI 批量档位

- 批次循环和正式导入沿用现有测试模式、WorkBuddy 写入开关、已验证 ERP API 及结果校验，不再额外要求工具策略验收闸门。审批助手不更改 WorkBuddy 客户端权限，也不能限制该客户端可调用的工具。正式使用前应由操作员核对客户端权限、清单范围和写入模式。
- `workbuddy.json_handoff_trial` 默认关闭。该协议目前通过隔离测试驱动验证：WorkBuddy 只读 `input.json` 与完整的分段规则文本，只提交 `judgments.json`；审批助手先冻结判定摘要，再在本机生成和回读 Excel。未确认送达、判定文件变更或缺少冻结摘要时不导入。旧试验结果不转为正式导入。

- 遇到「原投递未确认」时，先在 WorkBuddy 中核对原会话，不要重发或清除批次状态。源码部署可运行 `python scripts/check_workbuddy_dispatch.py "data/workbuddy/<批次ID>"` 查看投递状态、结果文件是否存在，以及本机对话记录能否唯一匹配。命令不发送、不导入、不修改数据；`unknown` 不表示未发送。
- 操作员已结案但投递不明的记录按清单号和 ERP 明细 ID 留置，规则更新或名称变化不会解除留置。原批次及迟到产物保留供审计，不得直接导入或删除状态来解锁。
- `workbuddy.auto_recover` 默认关闭。启用后，项目仅在本机 WorkBuddy 记录能唯一关联批次、会话与请求，且该请求明确报出已识别的 `Empty stream` 终止错误时，开新会话补跑一次。ERP 回读后只补跑原批次仍为空且身份一致的记录。旧批次的结果留存供审计，自动与手动导入均排除。仅超时、投递不明或 ERP 操作结果不明时保留原检查点。
- 审批进程异常退出后，已登记的任务可接续一次。Web UI 重启后等待旧进程退出和批次锁释放，再核对规则、ERP 环境与固定范围。人工停止仍在 Web UI 核对并恢复。Windows 开机启动独立配置。
- Web UI 的 WorkBuddy 批次循环默认选 20 条，20、30、50 条分别等待 15、20、25 分钟，尾批沿用所选档位。30、50 条须启用固定写表，依次通过隔离对照和真实满批试跑后，才能在本机的 `workbuddy.accepted_batch_sizes` 逐档放行。

### 恢复验收

1. 在专用 Windows 账号和模拟 ERP 中，使用相同 WorkBuddy 版本、模型、虚构输入与规则，对比 `2ad3806` 与 `d985ef4`。记录冷启动、前台复用、托盘恢复的窗口就绪、送达、文件落盘和校验用时；单独切换固定写表、接续、续聊和 JSON，每轮只改一项。
2. 管理员按 [WorkBuddy 权限与安全沙箱](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Permission-Modes) 配置专用客户端。用虚构任务验证命令、外部连接器、越界读写和 ERP 请求在执行前拦截，并确认本批文件读写仍成功。普通权限模式、提示词和事后日志不能替代拦截证据。
3. 三种窗口场景及故障注入均通过后，再另行确认一次真实批次零写入。先只读回查记录身份与状态，人工复核结果，禁止正式导入试验产物。另行授权的一条记录保存、回读及后续三轮人工监督验收，使用新批次，不接管已结案批次。
4. 尚无受支持的接口或受管策略供审批助手验证客户端有效权限时，建议保持人工监督，不开启无人值守。权限或数据核对失败时停止，不重发。

在没有生产凭据的专用环境运行 `python scripts/workbuddy_sandbox_acceptance.py prepare "<已存在的测试目录>"`，按输出的 `workspace` 打开虚构批次，使用 `prompt` 文件内容完成允许的读取和判定写入。确认 WorkBuddy 显示该批回执后执行 `python scripts/workbuddy_sandbox_acceptance.py verify "<root>" --receipt "<对话回执>"`。该命令校验两条已知判定和隔离目录外的虚构标记，生成并回读标准 Excel。它不会启动 WorkBuddy、连接 ERP 或签发权限证明。

默认生成的目录仅供创建账号访问。需要把**虚构**包交给另一个 Windows 账号时，在已确认该账号可访问的父目录下加 `--inherit-parent-acl` 重新生成；不要修改旧包 ACL、提权运行 WorkBuddy 或把真实批次放进共享目录。Windows ACL 允许访问后，仍需将输出的批次 `workspace` 设为 WorkBuddy 工作区，不要选整个公共目录。

负向验收由管理员在同一隔离客户端操作。仅用虚构目录和模拟端点，逐项保存与测试时间对应的**执行前拦截**记录：命令、外部连接器、工作区外文件读取和写入、模拟 ERP 请求。不要将真实凭据、规则或真实 ERP 用于负向探测。单凭测试文件未变、任务失败或未观察到工具调用不能通过此关。

可用 `python scripts/workbuddy_sandbox_acceptance.py audit "<root>" --transcript "<本轮会话 JSONL>"` 汇总与该虚构批次关联的工具调用。报告只显示工具分类和计数，不输出参数或文件内容。该命令只读；它能发现记录中的额外工具和越界路径，但不能证明未记录的调用被执行前拦截。

模拟 ERP 网络验收使用 `python scripts/workbuddy_sandbox_acceptance.py network-probe "<root>" --seconds 90`。它先以实际 TCP 请求确认虚构地址可达，再公布限时的 `127.0.0.1` 探测地址；管理员在该时间内测试 WorkBuddy 对此地址的访问。报告只保存次数和时间，不保存请求内容。命中意味着请求已到达，不得通过；零命中仍须与安全中心同一时段的执行前拒绝记录交叉核对。
- 通过隔离验收后，可将 `workbuddy.batch_size_canary` 临时设为 `{size: 30, list_number: "<清单号>"}`。在 Web UI 只勾选该清单，选择对应档位和「保存并生成试剂库」。一键匹配后须有足够空项，试跑只处理该清单一个满批。试跑结束后移除配置，核对保存、回读、入库和清理，再决定是否放行。50 条的试跑需先放行 30 条。

## 配置迁移

- 从「基础设置 → 配置导入与导出」导出 `.rabconfig`。到目标机器选择文件，输入原口令，预览差异后确认应用。活动任务、待恢复批次和待核对的 ERP 操作会阻止应用。
- 文件加密包含基本设置与凭据。目标机器的 WorkBuddy 安装路径、项目入口、自动恢复开关、已放行档位及 ERP 接口验收由本机管理。导入若变更 ERP 地址或账号，原接口写入验收会失效。规则和业务数据走各自迁移入口。
- 导入前的配置以 Windows 本机加密方式保存在 `data/backups/`。导入中途退出后，控制台重新启动时先恢复原配置，再加载设置。
